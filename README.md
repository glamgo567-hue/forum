# Forum API

Q&A-форум в духе Stack Overflow: вопросы с тегами, ответы, голосование и репутация пользователей. Асинхронный REST API на FastAPI.

## Стек

| Слой | Технология |
|---|---|
| Web | FastAPI, Uvicorn |
| ORM | SQLAlchemy 2.0 (async, `asyncpg`) |
| БД | PostgreSQL 16 |
| Миграции | Alembic |
| Аутентификация | JWT (`python-jose`), пароли через `passlib[bcrypt]` |
| Валидация | Pydantic v2, `pydantic-settings` |
| Тесты | pytest, pytest-asyncio, httpx |
| Линтер | Ruff |
| Инфраструктура | Docker, docker compose, GitHub Actions |

## Возможности

- Регистрация и вход по JWT, эндпоинт текущего пользователя.
- CRUD вопросов с автосозданием тегов и фильтрацией по тегу.
- CRUD ответов, принятие ответа автором вопроса (ровно один принятый ответ на вопрос).
- Голосование за вопросы и ответы (`+1` / `-1`) с автоматическим пересчётом репутации автора.
- Проверки владения на всех изменяющих эндпоинтах (403), запрет голосования и принятия собственного контента.
- Пагинация и детерминированная сортировка в списках.
- Анонимный доступ к чтению: `score` виден всем, `my_vote` возвращается только авторизованным.

## Быстрый старт

### Через Docker (рекомендуется)

```bash
cp .env.example .env
docker compose up --build
```

Миграции применяются автоматически при старте контейнера (`alembic upgrade head` в `CMD`). API поднимется на `http://localhost:8000`, интерактивная документация — на `http://localhost:8000/docs`.

### Локально

Приложению всё равно нужна БД, поэтому Postgres удобнее поднять из compose и запускать код на хосте:

```bash
docker compose up -d db

python -m venv venv && source venv/bin/activate
pip install -r requirements-dev.txt

cp .env.example .env      # DATABASE_URL уже указывает на localhost:5433
alembic upgrade head
uvicorn app.main:app --reload
```

Контейнер БД публикует порт как `127.0.0.1:5433:5432` — нестандартный порт выбран, чтобы не конфликтовать с системным PostgreSQL, а привязка к loopback не даёт базе торчать наружу.

## Переменные окружения

| Переменная | Назначение |
|---|---|
| `DATABASE_URL` | Подключение приложения к БД (`postgresql+asyncpg://...`) |
| `DATABASE_URL_DOCKER` | То же, но по внутреннему DNS compose (`db:5432`); подставляется сервису `web` |
| `SECRET_KEY` | Ключ подписи JWT |
| `ALGORITHM` | Алгоритм подписи, по умолчанию `HS256` |
| `ACCESS_TOKEN_EXPIRE_MINUTES` | Время жизни токена, по умолчанию `1440` |
| `POSTGRES_USER` / `POSTGRES_PASSWORD` / `POSTGRES_DB` | Инициализация контейнера БД |

Шаблоны: `.env.example` для разработки, `.env.test.example` для тестов. Оба реальных файла (`.env`, `.env.test`) в `.gitignore`.

## Тесты и линтер

Тесты идут против отдельной базы `forum_test` в том же контейнере. Её нужно создать один раз:

```bash
docker compose up -d db
docker compose exec db psql -U forum_user -d forum_db -c "CREATE DATABASE forum_test;"

cp .env.test.example .env.test
pytest
```

Проверка стиля:

```bash
ruff check .
```

`conftest.py` загружает `.env.test` до импорта приложения — это важно, потому что `app/dependencies/db.py` создаёт engine на этапе импорта модуля, и порядок импортов определяет, к какой базе он привяжется. Схема пересоздаётся перед каждым тестом через `create_all` / `drop_all`, зависимость `get_db` подменяется на тестовую сессию.

CI (`.github/workflows/tests.yml`) на каждый push и pull request в `main` поднимает Postgres как сервис, отдельным шагом проверяет применимость миграций и прогоняет весь набор тестов.

## Схема данных

```
users ──< questions ──< answers
  │           │            │
  │           └──< question_tag >── tags
  │           │            │
  └──< votes ─┴────────────┘
```

- `questions` ↔ `tags` — многие-ко-многим через `question_tag`.
- `votes` ссылается либо на вопрос, либо на ответ — ровно на один из двух. Это гарантирует `CheckConstraint`, а не только код приложения.
- Повторное голосование блокируется двумя частичными уникальными индексами: `(user_id, question_id) WHERE question_id IS NOT NULL` и `(user_id, answer_id) WHERE answer_id IS NOT NULL`. Обычный составной `UNIQUE(user_id, question_id, answer_id)` тут не работает: в PostgreSQL `NULL` не равен `NULL`, поэтому дубликаты проходили бы проверку.
- Удаление вопроса каскадно удаляет его ответы, голоса и связи с тегами (`ON DELETE CASCADE`).

## Репутация

| Событие | Изменение |
|---|---|
| `+1` за ответ | `+10` автору ответа |
| `+1` за вопрос | `+5` автору вопроса |
| Ответ принят | `+20` автору ответа |
| `-1` за вопрос или ответ | `-5` автору |

Изменение голоса пересчитывается как разница между новым и старым значением, удаление голоса откатывает начисление полностью.

При удалении вопроса снимается репутация как за голоса за сам вопрос, так и за голоса за все его ответы — включая репутацию их авторов, хотя удаление инициировал автор вопроса. Каскад на уровне БД сносит связанные строки, но `reputation` — обычная колонка, и о каскаде она не знает, поэтому откат считается в коде до удаления.

Начисление выполняется атомарным `UPDATE users SET reputation = reputation + :delta` — арифметику делает сама БД, поэтому одновременные голоса не затирают друг друга.

## Эндпоинты

Полная интерактивная спецификация — `/docs`.

### Аутентификация

| Метод | Путь | Доступ | Описание |
|---|---|---|---|
| `POST` | `/auth/register` | — | Регистрация |
| `POST` | `/auth/login` | — | Получение JWT (form-data) |
| `GET` | `/auth/me` | JWT | Текущий пользователь |

### Вопросы

| Метод | Путь | Доступ | Описание |
|---|---|---|---|
| `POST` | `/questions` | JWT | Создать вопрос, теги создаются автоматически |
| `GET` | `/questions` | — | Список; `skip`, `limit`, `tag` |
| `GET` | `/questions/{id}` | — | Вопрос по id |
| `PATCH` | `/questions/{id}` | автор | Изменить заголовок или текст |
| `DELETE` | `/questions/{id}` | автор | Удалить вопрос |

### Ответы

| Метод | Путь | Доступ | Описание |
|---|---|---|---|
| `POST` | `/questions/{id}/answers` | JWT | Ответить на вопрос |
| `GET` | `/questions/{id}/answers` | — | Список; `skip`, `limit` |
| `PATCH` | `/answers/{id}` | автор | Изменить текст |
| `DELETE` | `/answers/{id}` | автор | Удалить ответ |
| `PATCH` | `/answers/{id}/accept` | автор вопроса | Принять ответ |

### Голоса

| Метод | Путь | Доступ | Описание |
|---|---|---|---|
| `POST` | `/questions/{id}/vote` | JWT | Проголосовать; `409`, если голос уже есть |
| `PATCH` | `/questions/{id}/vote` | JWT | Изменить голос; `404`, если голоса нет |
| `DELETE` | `/questions/{id}/vote` | JWT | Снять голос |
| `POST` | `/answers/{id}/vote` | JWT | Аналогично для ответов |
| `PATCH` | `/answers/{id}/vote` | JWT | |
| `DELETE` | `/answers/{id}/vote` | JWT | |

Голосование намеренно разведено по трём методам вместо одного upsert-эндпоинта с переключением: так каждый метод имеет однозначную семантику и предсказуемый код ответа.

### Служебное

| Метод | Путь | Описание |
|---|---|---|
| `GET` | `/health` | Проверка живости |

## Известные ограничения

Это учебный портфельный проект, часть решений принята сознательно и в продакшене выглядела бы иначе.

- **Бонус `+20` за принятый ответ не откатывается.** Ни при переключении на другой ответ, ни при удалении принятого. Трактуется как исторический факт: человек однажды дал хороший ответ. Голоса, в отличие от этого, откатываются всегда.
- **Уникальность принятого ответа держится только кодом приложения**, без ограничения на уровне БД. Атомарность обеспечивается тем, что снятие старого и установка нового флага идут в одной транзакции.
- **Миграции запускаются из `CMD` контейнера.** Для одного инстанса это удобно, при нескольких репликах их пришлось бы выносить в отдельный шаг деплоя, иначе стартующие контейнеры будут конкурировать за одну и ту же миграцию.
- **Нет rate limiting и подтверждения email.**
- **Теги нельзя изменить через `PATCH` вопроса** — задаются только при создании.
- **Нет эндпоинта удаления пользователя**, поэтому `ON DELETE` для внешних ключей на `users` намеренно не настроен.
